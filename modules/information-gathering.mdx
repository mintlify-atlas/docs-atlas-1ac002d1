The Information Gathering module is the foundation of every WSTG-Scan assessment. Selecting option **2** from the main menu triggers a comprehensive enumeration phase that collects server metadata, inspects HTTP response headers, validates SSL/TLS certificate quality, identifies allowed HTTP methods, parses `robots.txt` and `sitemap.xml` for exposed paths, fingerprints the technology stack with WhatWeb, audits cookie security flags, and probes for CORS misconfigurations — all in a single automated pass before any active exploitation begins.

  </Card>

    Per-cookie audit for missing `Secure`, `HttpOnly`, and `SameSite` flags across every cookie in the session jar.

## How It Works

<Steps>
  <Step title="Initial Request and General Info">
    WSTG-Scan issues a GET request to the target URL and records the HTTP status code, `Server` header, all response headers, and the names of any cookies set. This baseline is stored in `SCAN_DATA["general"]` and used by every subsequent module.
  </Step>
  <Step title="Technology Fingerprinting via WhatWeb">
    The scanner invokes `whatweb` to extract CMS, framework, server, JavaScript library, and analytics information. Results are displayed in a colour-coded table.

    If WhatWeb is not installed, the scanner prompts to auto-install it:

    ```bash
    sudo apt-get install -y whatweb
    ```

    When WhatWeb is unavailable and the prompt is declined, technology detection falls back to inspecting `Server`, `X-Powered-By`, `PHPSESSID` cookies, and `ASP.NET` strings in response headers.

    <Note>
      If the session is authenticated, WhatWeb is invoked with the active session cookies and headers so that fingerprinting reflects the logged-in application state.
    </Note>
  </Step>
  <Step title="robots.txt and sitemap.xml Parsing">
    The module fetches `/robots.txt` and `/sitemap.xml`. All `Disallow:` and `Allow:` paths from `robots.txt` are extracted and stored in `SCAN_DATA["robots_paths"]`. These paths frequently reveal admin panels, backup endpoints, and other sensitive locations that are not linked from the main navigation.
  </Step>
  <Step title="HTTP Methods Enumeration">
    An OPTIONS request is sent to the target root. The `Allow` response header is parsed and every permitted method is recorded in `SCAN_DATA["http_methods"]`. A TRACE request is also sent — if it returns HTTP 200, the scanner flags it as Cross-Site Tracing (XST) and adds `TRACE` to the allowed methods list.
  </Step>
  <Step title="Security Header Audit">
    The response headers captured in step 1 are evaluated against five required security headers:

    | Header | Risk if Missing |
    |---|---|
    | `Strict-Transport-Security` | HTTPS not enforced; downgrade attacks possible |
    | `Content-Security-Policy` | XSS injection without script restriction |
    | `X-Frame-Options` | Clickjacking vulnerability |
    | `X-Content-Type-Options` | MIME-type sniffing attacks |
    | `Referrer-Policy` | Referrer leakage to third parties |

    Present headers are printed with their values in green; missing headers trigger a `[!]` warning.
  </Step>
  <Step title="Cookie Security Flags">
    Every cookie in the session jar is individually checked. The scanner warns for each cookie that is missing the `Secure` flag (cookie transmitted over plain HTTP), missing the `HttpOnly` flag (cookie accessible via JavaScript), or has a weak or absent `SameSite` attribute.
  </Step>
  <Step title="SSL/TLS Inspection">
    For HTTPS targets, a raw TLS handshake is performed using Python's `ssl` module against `hostname:443`. The certificate subject and negotiated protocol version are retrieved. Protocols older than `TLSv1.2` (e.g. TLS 1.0, TLS 1.1, SSLv3) are flagged as insecure.

    ```python
    # Excerpt from check_ssl_tls()
    context = ssl.create_default_context()
    with socket.create_connection((hostname, port), timeout=DEFAULT_TIMEOUT) as sock:
        with context.wrap_socket(sock, server_hostname=hostname) as ssock:
            version = ssock.version()   # e.g. "TLSv1.3"
    ```
  </Step>
  <Step title="Advanced CORS Analysis">
    The scanner tests multiple malicious origins against the target, including a generic external origin (`https://evil.com`), the `null` origin (used in sandboxed iframes), a subdomain-of-target variant, and a target-as-subdomain-of-attacker variant.

    For each origin, the scanner checks:
    - **Wildcard + credentials**: `Access-Control-Allow-Origin: *` combined with `Access-Control-Allow-Credentials: true` — this combination is treated as critical.
    - **Reflected origin**: when `Access-Control-Allow-Origin` echoes back the supplied `Origin` header, indicating a dynamic reflection policy.
    - **Preflight with malicious origins**: an OPTIONS preflight is sent with `Access-Control-Request-Method: POST` and `Access-Control-Request-Headers: Authorization` to verify whether the server accepts cross-origin authenticated requests.
  </Step>
</Steps>

## Security Header Details

The following five headers are audited on every information gathering run:

<Accordion title="Strict-Transport-Security (HSTS)">
  HSTS instructs browsers to only connect via HTTPS. Its absence means an attacker on the same network can downgrade connections to plain HTTP. A recommended value is `max-age=31536000; includeSubDomains; preload`.
</Accordion>

<Accordion title="Content-Security-Policy (CSP)">
  CSP restricts which origins can load scripts, stylesheets, and other resources. Without it, injected scripts execute freely. The scanner reports presence or absence; evaluating the policy's strictness is a manual follow-up step.
</Accordion>

<Accordion title="X-Frame-Options">
  Prevents the page from being embedded in a `<frame>` or `<iframe>` on another origin, blocking clickjacking. Valid values are `DENY` or `SAMEORIGIN`.
</Accordion>

<Accordion title="X-Content-Type-Options">
  The value `nosniff` prevents browsers from MIME-sniffing responses away from the declared `Content-Type`. Its absence can enable content-injection attacks via uploaded files.
</Accordion>

<Accordion title="Referrer-Policy">
  Controls how much referrer information is included with navigations. A missing or overly permissive policy can leak internal URLs, session tokens in query strings, or user data to third-party services.
</Accordion>

## CORS Vulnerability Severity Matrix

| Condition | Severity |
|---|---|
| `Access-Control-Allow-Origin: *` + `Access-Control-Allow-Credentials: true` | **Critical** — any origin can make credentialed requests |
| Origin reflected with `Access-Control-Allow-Credentials: true` | **High** — attacker-controlled site can read authenticated responses |
| Origin reflected without credentials | **Medium** — cross-origin reads possible for unauthenticated resources |
| `Access-Control-Allow-Origin: *` without credentials | **Low / Info** — public resources accessible cross-origin |
| Preflight accepts POST + Authorization from evil origin | **Info** — note for manual review |

## Data Stored for Reports

All findings from this module are merged into `SCAN_DATA["general"]` and `SCAN_DATA["robots_paths"]`, contributing to every report format:

```json title="SCAN_DATA['general'] structure"
{
  "status_code": 200,
  "server": "nginx/1.24.0",
  "technologies": [
    { "name": "WordPress", "detail": "6.5.3" },
    { "name": "PHP", "detail": "8.2.0" }
  ],
  "technologies_source": "whatweb",
  "headers": {
    "Strict-Transport-Security": "max-age=31536000",
    "X-Content-Type-Options": "nosniff"
  },
  "cookies": ["session", "csrftoken"]
}
```

<Tip>
  Run the Information Gathering module first in every assessment. Its results — server version, technology stack, cookie names, and robots.txt paths — are consumed by later modules including injection tests, source code analysis, and the HTML dashboard report.
</Tip>
