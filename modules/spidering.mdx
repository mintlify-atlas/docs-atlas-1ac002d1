The Spidering module (menu option **7**) performs a breadth-first crawl of the target application, building a complete map of reachable URLs, query parameters, and HTML forms. The results are stored in `SCAN_DATA["spider"]` and reused by two downstream modules — the **Injection Tests** (option 9) and the **Source Code Analysis** (option 8) — so a thorough spider run before either of those modules dramatically expands coverage without requiring duplicate HTTP requests.

## How the Crawler Works

The spider uses a standard BFS queue (`collections.deque`) seeded with the target URL. At each step it fetches a page, extracts all `<a href>` links and form actions from the same domain, and enqueues any newly discovered URLs up to the configured depth limit.

```python title="BFS queue structure (from spider_website)"
urls_queue = deque()
urls_queue.append((target_url, depth=0))

while urls_queue and len(visited) < max_pages:
    current_url, depth = urls_queue.popleft()
    if depth > max_depth:
        continue
    # fetch, parse, enqueue children at depth+1
```

A `tqdm` progress bar shows the number of pages visited and URLs discovered when the `tqdm` library is available. Without it, a progress update is printed every 20 pages.

## Configuration Options

When you select option 7, three parameters are prompted interactively:

<ParamField path="max_pages" type="integer" default="500">
  Maximum number of HTML pages to visit. The crawler stops once this limit is reached even if the queue is not empty. Useful for limiting runtime on large sites.
</ParamField>

<ParamField path="max_depth" type="integer" default="3">
  Maximum BFS depth from the seed URL. A value of 3 means: seed → level 1 links → level 2 links → level 3 links. Deeper crawls discover more but take proportionally longer.
</ParamField>

<ParamField path="use_robots" type="boolean" default="true">
  When `true`, the crawler loads `robots.txt` at startup and skips any URL that the `*` user-agent is disallowed from fetching. Set to `false` to crawl without restrictions (only do this on systems you control or with explicit permission).
</ParamField>

```text title="Interactive Prompts"

> 200

[?] Profundidad máxima de rastreo (default 3):
> 4

[?] ¿Respetar robots.txt? [S/n]:
> S
```

## Redirect Handling

The spider uses a `requests.Session` with `MAX_REDIRECTS = 10`. For pages that exceed the redirect limit, WSTG-Scan catches `requests.exceptions.TooManyRedirects` and **does not abort** — instead it retries the request with `allow_redirects=False` to capture the raw redirect target. This means redirect chains on the target site do not halt the crawl.

```python title="TooManyRedirects handling (from spider_website)"
try:
    resp = session.get(current_url, timeout=DEFAULT_TIMEOUT)
except requests.exceptions.TooManyRedirects:
    # Retry without following redirects — still capture the URL
    try:
        resp = session.get(current_url, timeout=DEFAULT_TIMEOUT,
                           allow_redirects=False)
    except Exception:
        continue
```

## Form Detection and Deduplication

For every HTML page visited, WSTG-Scan uses BeautifulSoup to find all `<form>` elements. For each form, it extracts:

- **Action URL** — resolved to an absolute URL relative to the current page
- **Method** — `GET` or `POST` (defaults to `GET` if unspecified)
- **Input names** — all `<input>`, `<textarea>`, and `<select>` names, **excluding** types `submit`, `button`, `image`, `reset`, and `file`

The exclusion of non-data input types means the injection module only tests fields that actually carry user-controlled data, avoiding wasted payloads against submit buttons.

### Form Deduplication

Many applications render the same navigation bar or login form on every page. Without deduplication, a site with 100 pages and a shared login form in the navbar would produce 100 identical form entries. WSTG-Scan deduplicates forms by a composite key:

```python title="Form deduplication key (from spider_website)"
form_key = (
    form_action_url,          # resolved absolute URL
    method,                   # "GET" or "POST"
    tuple(sorted(set(form_inputs)))  # sorted, deduplicated input names
)
if form_key in form_keys_seen:
    continue
form_keys_seen.add(form_key)
```

This means a login form appearing on every page is only counted and tested once — significantly reducing noise in injection test results.

## URL Scope Restriction

The spider only follows links whose `netloc` matches the target domain. External links (social media, CDNs, third-party APIs) are discovered and recorded but never followed, keeping the crawl focused on the target application.

## Output and Results

When the crawl completes, a summary is printed and stored:

```text title="Spider Completion Output"
[+] Spidering completado. Páginas visitadas: 87, URLs únicas descubiertas: 312
[INFO] Parámetros únicos encontrados: 24 -> id, page, q, user, redirect, ...
[INFO] Formularios detectados durante el spidering: 8
```

Results are saved to `SCAN_DATA["spider"]`:

```json title="SCAN_DATA['spider'] structure"
{
  "total_urls": 312,
  "total_params": 24,
  "total_forms": 8,
  "sample_urls": [
    "https://example.com/",
    "https://example.com/login",
    "https://example.com/profile?id=1"
  ],
  "sample_params": ["id", "page", "q", "redirect", "user"],
  "sample_forms": [
    {
      "page_url": "https://example.com/login",
      "action": "https://example.com/auth",
      "method": "POST",
      "inputs": ["username", "password", "csrf_token"]
    }
  ]
}
```

## Downstream Module Integration

<CardGroup cols={2}>
  <Card title="Injection Tests (Option 9)" icon="syringe">
    The injection module consumes `sample_forms` and `sample_params` directly from `SCAN_DATA["spider"]`, testing each form input and GET parameter with SQL injection, XSS, path traversal, command injection, and open redirect payloads.
  </Card>
  <Card title="Source Code Analysis (Option 8)" icon="code">
    The source code module reuses `sample_urls` as the seed list for downloading HTML pages and linked JavaScript, JSON, and source map files. Running the spider first expands coverage from a single target URL to hundreds of application pages.
  </Card>
</CardGroup>

<Tip>
  Always run the Spider (option 7) before the Injection Tests (option 9) and Source Code Analysis (option 8). The spider's output directly feeds both modules — without it, injection tests only have access to the target's root URL parameters and source code analysis only downloads the landing page.
</Tip>

<Note>
  The spider only processes `text/html` responses. Non-HTML content types (JSON APIs, file downloads, images) are skipped during crawling, though their URLs are recorded and can be visited by the source code analysis module.
</Note>
